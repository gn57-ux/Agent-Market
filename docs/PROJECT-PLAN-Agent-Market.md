# Agent Market 项目实施计划

> 版本：v1.4
> 日期：2026-08-27
> 依据：一期 PRD v1.2、二期 PRD v1.2、手写白板、《Web3+AI 智能体平台产品流程与开发指导》《AI Agent平台开发指导与面试备战》两份最新会议纪要
> 变更摘要：整体剩余开发压缩为两天；优先补齐手写白板基本要求，再吸收两份会议纪要中与 Agent Market 直接相关且可验证的最小增量，删除重复建设并明确延期项。

## 1. 结论

项目按“先证明资金与履约闭环，再增强智能化”的顺序实施：

1. 一期用固定测试代币、单 Agent 任务、V0 规则撮合和简单仲裁，完成可复现的 Web3 任务闭环。
2. 整体剩余开发采用两天时间盒，只交付可真实演示的增强 MVP，不以压缩测试或伪造 AI/数据能力换取“完成”。
3. 后续生产化阶段根据真实用户、数据和故障证据扩展完整多 Agent、CTR、可靠异步和办公室社交，不设为当前答辩阻断项。
4. 首页使用 Three.js 构建“意图路由星图”，但作为可动态加载、可暂停、可静态降级的展示层，不参与钱包和资金状态判断。
5. 普通 UI、图标、动效和三维素材优先复用公开组件库与资源库，项目定制集中在领域流程、品牌主题和推荐可解释性。

## 2. 开发前的问题定义

### 2.1 当前行为

- 已有两份详细 PRD，但尚未看到实现代码和可运行基线。
- 课程要求涵盖 Agent 上传、任务发布、V0、V1、钱包、Go、PostgreSQL、合约和工程质量。
- 原始设想还包含 CTR、多 Agent、SQS/DLQ、ECS/Cloudflare、手续费和理财收益，全部一次实现会导致范围失控。

### 2.2 期望行为

一期答辩时，需求方可以连接测试钱包、发布并锁定预算；后端独立复核交易；Go 引擎返回“2 个高分候选 + 1 个新人探索位”；候选支付 6% 质押后接单；Agent 提交成果；需求方验收、争议或触发超时结算；链上资金与链下资料能够互相追溯。

二期答辩时，系统先证明语义相关但标签不完全相同的 Agent 能被 V1 找到，并且故障时回退 V0；随后再展示多 Agent 子任务协作。没有真实样本时，只展示 CTR 数据闭环、训练管线和影子结果，不宣称模型提升线上效果。

### 2.3 已知事实与假设

| 类型 | 内容 | 处理方式 |
|---|---|---|
| 已知 | React + TypeScript + Vite + viem | 前端固定栈 |
| 已知 | Fastify + Zod + PostgreSQL | API 与业务数据主栈 |
| 已知 | Go Dispatch Engine | 单点拥有资格、评分、探索和解释规则 |
| 已知 | Solidity + Hardhat | 单点拥有资金和任务结算状态 |
| 已知 | 首页使用 Three.js | 独立展示模块，必须可降级 |
| 假设 | 一期使用 YD 测试 ERC-20 | 开发前 ADR 确认精度与网络 |
| 假设 | Agent 调用可先人工模拟交付 | 第 1 周确认是否真实调用外部 Agent API |
| 假设 | 一期由指定地址二选一仲裁 | 高级委员会放到二期可选项 |
| 假设 | 验收窗口为 72 小时 | 合约参数化，测试使用时间加速 |

### 2.4 输入、输出与失败场景

- 输入：Agent 资料、分类与技能；任务描述、等级、预算与期限；钱包签名和交易；成果与证据。
- 输出：已发布任务、推荐候选及解释、链上资金状态、成果哈希、结算结果、评分与审计轨迹。
- 关键失败：错误网络、余额或授权不足、拒签或回滚、错误交易哈希、RPC 故障、无候选、并发接单、逾期、重复结算、WebGL 不可用、公开资源许可不明。
- 成功证明：自动化测试、资金守恒不变量、可重复 E2E、交易和事件证据、静态降级截图、干净环境启动脚本。

### 2.5 2026-08-27 最新会议输入及解释边界

最新会议要求保留一期“登录 - 质押 - 发布 - 匹配 - 执行 - 支付”闭环，并将下列能力作为下一阶段重点：

- Privy 钱包登录，不接受只有演示外观而没有真实会话的实现。
- Agent 增加自动接单、免费/付费、作者简介和平台协议兼容信息；免费 Agent 可进入市场，付费 Agent 经可用性审核后展示。
- Job 增加支付类型、优先级和自动分配意愿。
- Dashboard 汇总已发布任务、已发布 Agent、已签约 Agent 和争议事项。
- 展示开发者收入、任务预算和合约质押三类资金视图。
- 评分采用历史成功率 70%、雇主评价 15%、专业度 10%、仲裁记录 5%，并考虑阈值、洗牌和时间衰减。
- 多 Agent 支持系统建议、用户手动调整和 LangGraph 自动执行；上一步输出作为下一步输入。
- 个人虚拟办公室为应做能力；访问他人办公室的社交功能仍为可选扩展。

会议纪要是最新需求输入，但不是可以跳过设计与安全评审的实现命令。以下解释在二期启动前必须保持：

1. “三钱包”先解释为三个可核对的资金域/资金视图；是否创建三个真实钱包、使用 Privy embedded wallet 或仅做链上地址与账本聚合，须经过单独 ADR，平台不得默认托管用户私钥。
2. Privy 与一期 MetaMask 会话必须有迁移与回滚方案，不允许一次替换导致已有地址身份失效。
3. “平台指定协议”必须由版本化请求/响应契约、兼容性测试和审核状态表达，不绑定未经确认的第三方框架。
4. 多 Agent 同时执行和结果择优属于二期工作流，不修改一期单 Agent 任务的既有结算语义。
5. 评分权重是业务基线，唯一实现归属 Go Dispatch Engine；AI 专业度评测不得把密钥、完整提示词、敏感响应或错误日志发送给未批准的模型提供方。

第二份会议纪要同时讨论了 BERT 意图分类和知识图谱/RAG，但其问题背景是高风险 AI 客服，不能自动转化为 Agent Market 的两天需求。两天内只复用其工程原则：先分类/资格门禁，再进入自动化；固定事实通过检索或工具获得，不让模型凭提示词虚构。训练 BERT、知识图谱客服和 Qwen 路由不计入 Agent Market 当前完成定义。

## 3. 架构方案比较

### 3.1 后端边界

| 维度 | 方案 A：一期完整微服务 | 方案 B：模块化 Fastify + 独立 Go 引擎 |
|---|---|---|
| 接口复杂度 | 高，跨服务契约多 | 中，外部边界只有 Go、RPC 和合约 |
| 模块依赖 | 分布式状态多 | 数据事务集中，资金规则仍在合约 |
| 信息隐藏 | 取决于服务边界质量 | Go 隐藏推荐，合约隐藏结算，Fastify 隐藏业务资料 |
| 可测试性 | 环境成本高 | 本地可分别单测并做 E2E |
| 修改成本 | 一期过高 | 适合课程周期 |
| 回滚 | 多服务协同回滚 | API、Go 和合约按版本独立回滚 |

选择方案 B。只有出现独立状态、资源需求或故障模式时，二期才拆 Workflow Worker、Chain Indexer 和 Training Pipeline。

### 3.2 Three.js 实现

| 维度 | 方案 A：原生 Three.js 深模块 | 方案 B：React Three Fiber 组件树 |
|---|---|---|
| React 耦合 | 低 | 中至高 |
| 生命周期 | 手动但集中 | 声明式但可能分散 |
| 依赖 | 少 | 增加渲染抽象 |
| 高频动画状态 | 不进入 React | 容易误入 React 状态 |
| 回滚 | 可直接关闭 Canvas | 需要卸载组件树 |

一期选择方案 A，只暴露 `mount`、`pause`、`resume`、`dispose`。若二期出现大量可交互三维页面，再评审方案 B。

### 3.3 公开组件和资源

方案 A 是自行实现所有 UI 和动画资产，品牌自由度高但交付慢、无障碍和边界错误多。方案 B 是复用成熟公开组件、图标、Three.js addon、shader、纹理与模型，再统一主题并组合成业务页面。

选择方案 B，但设置准入清单：

- 许可证允许课程展示、修改与分发，并记录来源和版本。
- React 组件支持 TypeScript、键盘操作、焦点管理和主题定制。
- 同类能力只保留一个主要来源，避免组件库叠加。
- 三维资产经压缩并设置体积预算；移动端有低模或静态替代。
- 不直接复制来源不明的整页代码；引入代码仍需测试、Lint 和人工解释。
- 对公共组件只做建立主题或领域边界的封装，不创建字段搬运式浅包装。

## 4. 一期实施路线：6 周

### 第 0 步：冻结决策，1-2 天

- 确认测试网、代币精度、预算上下限、验收窗口、仲裁地址和 Agent 是否真实调用。
- 建立 ADR、环境变量清单、Monorepo、统一命令和 CI 骨架。
- 为公开组件/资源建立 `THIRD_PARTY_NOTICES` 或等效清单。

退出条件：所有会影响合约构造参数或数据模型的决策有唯一记录。

### 第 1 周：契约与静态骨架

- 固定任务状态机、链上字段、链下表和 OpenAPI 草案。
- 完成首页、任务创建、Agent 创建和任务详情静态原型。
- 选定一个主要 UI 基础组件来源、图标来源和 Three.js 资源策略。
- 建立钱包/RPC/Go 的 mock，使前端不等待后端完成。

退出条件：状态转换评审通过；页面可在无钱包、无 WebGL 时展示和操作静态流程。

### 第 2 周：合约纵切

- 实现 YDToken、演示 Faucet 和统一 TaskEscrow。
- 覆盖预算托管、6% 质押、接单、提交、验收、两类超时、争议和取消。
- 加入接单授权防重放、权限、重入和资金守恒测试。

退出条件：Hardhat 编译与测试通过，所有终态资金可核算。

### 第 3 周：Fastify 业务纵切

- 实现签名登录、Agent、任务草稿、成果、争议和评分模块。
- Zod 作为系统边界，PostgreSQL 迁移可重复执行。
- 实现交易复核：链、合约、事件、任务、地址、金额、确认数和唯一交易哈希。
- 只保存 Agent 凭据引用，不把秘密写入业务库或日志。

退出条件：API 集成测试覆盖正常与错误交易；重复请求不产生重复业务结果。

### 第 4 周：Go V0 撮合纵切

- 完成资格过滤、Jaccard 标签相似度、完成率、质量分和稳定排序。
- 完成两个高分位、一个新人探索位和结构化解释。
- 保存算法版本和推荐快照；Fastify 生成候选接单授权。

退出条件：黄金样本、候选不足、新人为空、同分和 1000 Agent 基准测试通过。

### 第 5 周：前端和 Three.js 纵切

- 串通钱包、创建任务、预算授权、锁定、推荐、接单质押、提交和结算。
- Three.js 实现意图进入、扫描、三个候选、质押、交付和结算叙事。
- Canvas 动态加载；隐藏、离屏时暂停；卸载释放资源；WebGL/低动态偏好时显示静态图。
- 公开组件完成表单、弹层、通知、表格和导航，统一主题令牌。

退出条件：正常 E2E 通过；移动端、键盘、减少动态效果和 WebGL 失败路径通过。

### 第 6 周：稳定、证据与答辩

- 完成并发接单、Agent 逾期、需求方逾期和至少一条争议路径。
- 统一错误文案、日志关联字段和区块浏览器入口。
- 完成 README、演示数据、部署脚本、架构图、答辩脚本和第三方许可清单。
- 冻结功能，只修复阻断演示或资金正确性的问题。

退出条件：全部质量门禁通过；干净环境可复现；正常流程和至少一个异常流程可稳定演示。

## 5. 两天整体交付路线

### 阶段一：基础交易闭环收尾

现有功能不再扩张。完成集成分支最终 N6、人工 QA、合并 main 和合并后 smoke test即退出。

### 第一天：一期收口 + 白板数据与协议缺口

1. 完成一期集成分支最终 N6；只有门禁全绿并经人工确认后，才将已验证结果作为第二天基线。
2. 不重做一期已有的 Agent/任务、最多 3 个候选、YD Token/Faucet、MetaMask、6% 质押、交付、争议和结算。
3. 补充 Agent 作者简介、调用地址、平台协议版本和凭据引用；`key` 不得以明文进入数据库、API、URL、日志或测试快照。
4. 补充任务专家类型；不新增重复的分类、标签、预算或钱包模型。
5. 为创建与 Agent 调用定义幂等请求 ID；同键同输入返回同结果，同键不同输入拒绝。
6. 如时间允许，增加免费/付费和自动分配布尔字段，但不建设后台审核工作流。

第一天退出门禁：一期全栈基线可重复；新增迁移 up/down/up；权限、SSRF/调用地址、凭据脱敏和幂等有回归测试。

### 第二天：向量匹配 + 评分 + 最终演示

1. 在现有分类、标签、资格过滤和新人探索之后接入 pgvector/真实 Embedding Provider，返回仍限制为最多 3 个候选。
2. Provider 失败、超时或无向量时自动回退现有 V0，不阻断任务交易闭环。
3. 在 Go 中集中补齐完成强度、质量反馈、沟通体验、争议率和历史完成规模；缺失值、窗口和范围必须明确。
4. 保存算法版本、规范化输入摘要和推荐解释；用小型人工标注集及黄金样本验证。
5. 在现有 Agent/任务页面展示新增字段和推荐解释；不新建 Dashboard 或资金账本。
6. 运行真实 PostgreSQL、Go、Hardhat/RPC、API、Web、浏览器和完整一期回归，生成白板/会议要求验收矩阵。

第二天退出门禁：向量故障可靠降级；资格门禁不可绕过；评分可解释可回放；`0.21` 与合成 CTR 未进入系统；一期资金闭环无回归。

### 阶段三：按真实证据推进的生产化扩展

阶段三没有预设必须全部实现的日期，按真实需求逐项启动：

- Privy 适配、完整免费/付费 Agent 审核和三类资金视图。
- LangGraph、多 Agent DAG、并行节点、局部重试、重新匹配和复杂资金分配。
- outbox、队列、DLQ、独立 Worker 和链索引服务。
- 完整 AI 专业度评测、申诉与反作弊。
- CTR 数据集、模型登记、影子排序和满足门槛后的灰度。
- 使用 Cocos Creator 建设一套个人虚拟办公室，再在同一模块上扩展他人访问、隐私、访客和社交；2D/轻量 3D 只选择一种初始 renderer。
- BERT 客服意图模型、知识图谱/RAG 客服和 Qwen 客服路由；它们属于独立客服产品纵切，不与 Agent Market 匹配模块混做。
- 高级仲裁、云工程化和规模性能优化。

阶段三不得反向阻塞阶段二 MVP，也不得把未实现项目计入阶段二完成。

## 6. 质量门禁

每个纵切完成后运行与风险相称的检查，最终至少包括：

- TypeScript 类型检查、Lint、格式和生产构建。
- Fastify 单元/集成测试和数据库迁移测试。
- Go 测试、格式、静态检查和基准测试。
- Hardhat 编译、单元测试和资金守恒不变量。
- 正常、超时、争议、错误网络、错误金额、重复交易和并发接单 E2E。
- Three.js 资源释放、静态降级、移动端性能、减少动态效果和可访问性检查。
- 第三方资源许可证、来源、版本、体积和安全审查。

无法执行的检查必须记录原因、影响、风险和补测计划，不以删除测试或降低标准换取通过。

## 7. 开发顺序约束

- 新功能和重构分开提交、分别验证。
- 先完成一条最小纵向成功路径，再扩展异常状态和页面，不按技术层一次铺满所有模块。
- 资金规则只属于合约，推荐公式只属于 Go，引导文案不能成为业务事实源。
- 链下状态是已确认链上状态的投影；前端不根据本地布尔值推断资金终态。
- 二期只预留稳定 ID、版本字段、事件契约和接口，不在一期创建无消费者的空服务。

## 8. 项目完成定义

一期完成不是“页面能点”，而是以下证据同时存在：

- 一次正常发布、推荐、接单、交付和结算的交易证据。
- 至少一个超时或争议异常流程证据。
- 合约、API、Go、前端和 E2E 测试报告。
- Three.js 完整动画与静态降级证据。
- 链上事件、链下操作历史和资金核算可以互相解释。
- 所有关键设计能说明选择理由、依赖条件、失败方式和回滚方法。
- 干净环境按照 README 可以启动、初始化演示数据并重复答辩流程。
