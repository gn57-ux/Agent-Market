# Privy embedded wallet 威胁模型

- 相关 Feature/Task：Feature 16（identity-agent-review-funds-dashboard）/ T-1610
- 相关 ADR：`docs/adr/0002-privy-embedded-wallet.md`
- 日期：2026-09-01
- 状态：已批准（用户 2026-09-01 批准，AC-1608 满足；批准时追加 3 项强制 T-1601 验证要求——令牌重放/撤销测试、伪造/篡改令牌拒绝测试、前端令牌存储与 CSP 核查，见 tasks.md T-1601 v1.2）

## 范围

本威胁模型只覆盖"本项目集成 Privy embedded wallet"这一新增信任边界引入的风险，不重复分析 Privy 自身 TEE 架构内部的安全性（那是 Privy 的责任范围，本项目作为使用方只能验证其公开承诺，不能审计其内部实现）。既有的合约资金安全（`TaskEscrow` 放款/退款/仲裁权限校验）、既有的 SIWE 登录路径威胁，均已在 Feature 4/Feature 2 的既有验收中覆盖，不在本文档重复。

## 信任边界图（文字描述）

```
用户浏览器 --(登录)--> Privy SDK（前端） --(Privy 签发的访问令牌)--> 本项目前端
                                                                      |
                                                    (把令牌作为 proof 提交)
                                                                      v
                                          本项目后端 PrivyIdentityProvider.completeAuth
                                                                      |
                                            (拿令牌向 Privy 验证/或本地校验 JWT 签名)
                                                                      v
                                                          Privy 基础设施（验证服务）
                                                                      |
                                                        (验证结果：令牌有效 + 绑定地址)
                                                                      v
                                          本项目后端只保留验证结果，令牌本身立即丢弃
                                                                      |
                                            (IdentityVerificationResult { address })
                                                                      v
                                              本项目其余全部业务模块（不变，见 T-1600）
```

**N4 Codex 审查真实发现并已修正的错误（P1）**：早期版本的这张图声称本项目后端"绝不接触"Privy token，这是错的——后端必须真实接收前端提交的 Privy 访问令牌（作为 `IdentityProvider.completeAuth` 的 `proof` 参数，T-1600 已建立的接口天然支持这种任意 provider 特定证明形状），并且必须真实验证这个令牌（调用 Privy 验证 API，或本地校验 Privy 签发 JWT 的签名），才能确认发起请求的人真的通过了 Privy 认证、真的拥有这个地址——如果后端从不接收任何令牌，就无法区分"真实登录"和"任意调用方声称自己是某个地址"，等同于认证形同虚设。**真正的约束是**：本项目后端可以、也必须在验证阶段接收令牌，但验证完成后必须立即丢弃，不得持久化、不得写入日志、不得原样出现在任何 API 响应体里——`completeAuth` 返回给调用方的只有 `IdentityVerificationResult { address }`，令牌本身的生命周期到 `completeAuth` 内部结束。这与本文档"风险清单"里"公共 API 响应体/错误信息/日志意外包含 Privy 原始 token"这条风险的缓解措施是一致的，本次只是修正了图示，风险清单本身的措辞（"绝不出现在日志/响应体"）从一开始就是准确的。

真实新增的信任边界有两条：**本项目前端 ⟷ Privy 基础设施**（令牌签发，由 Privy 官方前端 SDK 负责，本项目不重新实现）；**本项目后端 ⟷ Privy 基础设施**（令牌验证，`PrivyIdentityProvider` 内部真实发起的调用，T-1601 实现范围）。

## 风险清单

| 风险 | 真实来源（非假设） | 可能性 | 影响 | 缓解措施（本项目侧，具体到实现） |
|---|---|---|---|---|
| **本项目前端被攻破（XSS/恶意依赖/不安全的令牌存储），攻击者直接窃取浏览器里活跃的 Privy 访问令牌，或直接驱动已认证的 Privy SDK 发起真实的 embedded-wallet 签名请求** | N4 Codex 审查真实发现（第二轮）：这是 embedded wallet 相对纯 MetaMask 真实新增的攻击面——MetaMask 场景下 XSS 最多诱导用户在扩展弹窗里误批准一笔交易，用户至少有一次真实可感知的确认动作；embedded wallet 场景下，一旦前端被攻破，攻击者可以在用户毫无感知的情况下，用浏览器里已经建立的真实 Privy 认证会话，静默、自动化地反复请求签名，这是本文档修正前完全遗漏的路径 | 中——取决于本项目前端自身的依赖供应链/XSS 防护是否到位，不是 Privy 的责任范围 | 极高——一旦得手是真实、可自动化、用户无感知的资金损失，且不需要攻破 TEE 或窃取后端凭据 | 这是**前端**的真实防护要求，T-1601 实现范围需要包含：①Privy 访问令牌不落地到 `localStorage`/可被第三方脚本读取的存储，优先使用 Privy SDK 自身推荐的、生命周期受控的内存态/httpOnly 存储方式；②严格 CSP（禁止内联脚本、限制可加载的脚本来源），降低 XSS 注入面；③前端依赖锁定+审计（`pnpm audit`/锁文件完整性），降低"恶意依赖注入"这条路径的概率；④令牌生命周期尽量短，缩小失窃后的可利用窗口；⑤`PrivyIdentityProvider`/前端集成必须有真实测试：令牌失效/撤销后，用旧令牌重放请求必须被拒绝（不是假设 Privy 会处理，需要真实验证一次）。这条风险本项目无法完全消除（属于"该防线是浏览器安全，不是身份提供方架构安全"这一类真实存在、无法归零的残留风险），T-1601 完成后必须在验收报告里明确写清这一点，不得含糊带过 |
| 后端接受了前端提交的 Privy 访问令牌，但未真实验证（或验证逻辑有漏洞）就信任其中的地址声明 | N4 Codex 审查真实发现（本文档修正前的图示错误暴露了这个盲区——如果误以为后端"不接触令牌"，就可能实现成"直接信任前端声称的地址"，等同于认证被跳过） | 低（只要 T-1601 严格按 Privy 官方验证方式实现），但后果极其严重，必须显式列为风险而非隐含假设 | 极高——任意调用方可以冒充任意地址登录，等同于认证完全失效 | `PrivyIdentityProvider.completeAuth` 必须对令牌做真实验证（调用 Privy 官方验证 API，或本地校验 JWT 签名+有效期+audience/issuer），验证失败必须返回 `{ok:false, reason:"invalid_proof"}`（复用 T-1600 已有的 `CompleteAuthResult` 类型，不新增分支）；T-1601 的验证清单必须包含一条"伪造/篡改令牌必须被拒绝"的真实测试，不能只测试"合法令牌能登录成功"这一条正向路径 |
| Privy 后端 API 凭据（bearer token/webhook secret）泄漏 | Privy 官方文档明确承认："若 API 凭据被盗，攻击者可用 auth share 请求签名" | 中——取决于本项目自身凭据管理是否规范 | 高——凭据泄漏等价于攻击者可代表任意用户发起签名请求 | 凭据以平台级环境变量形式管理（与 `BACKEND_RPC_URL`/`ACCEPTANCE_PERMIT_SIGNER_KEY` 等既有平台级密钥同一模式，直接 `process.env.PRIVY_*` 读取，不经过 `credential.ts` 的 `env://AGENT_<uuid>` 机制——N4 Codex 审查真实发现：那套机制的解析器专门只接受 Agent 凭据的 UUID 格式，不是通用密钥引用方案，详见 `privy-embedded-wallet-key-management.md`），绝不硬编码、绝不落库明文、绝不出现在日志（复用既有 `logging.integration.test.ts` 的日志内容审查模式，扩展覆盖 Privy 凭据） |
| TEE（AWS Nitro Enclave）完整性被攻破 | Privy 官方文档承认这是整个模型的信任根 | 低（Privy 自身安全投入，非本项目可控） | 极高——密钥隔离完全失效 | 本项目无法直接缓解（第三方基础设施风险），只能：①在 ADR 的"失败条件"里把"Privy 公开披露过真实 TEE 安全事件"设为强制重新评审触发点；②不把 embedded wallet 作为唯一登录路径（F-1603 SIWE 长期并存），给用户真实的退出路径 |
| 公共 API 响应体/错误信息/日志意外包含 Privy 原始 token 或 SDK 内部对象 | 本项目自己实现 `PrivyIdentityProvider` 时的真实实现风险，不是第三方风险 | 中——取决于实现是否严格遵守 T-1600 已建立的投影边界 | 高——一旦发生即是本项目自己的责任事故，AC-1602 明确要求真实抓包/日志审查证据 | `IdentityVerificationResult` 类型层面只暴露 `address`（T-1600 已建立），`PrivyIdentityProvider.completeAuth` 内部任何 Privy SDK 返回值必须在函数返回前完成投影，不得原样传递或部分展开；AC-1602 的抓包/日志审查在 T-1601 实现完成后必须真实执行一次，不能只做代码走查 |
| Privy 服务不可用/网络故障导致登录功能整体不可用 | 真实的第三方依赖可用性风险 | 中 | 中——用户无法登录，但资金安全不受影响（Privy 不可用不代表资金被盗，只是登录功能降级） | SIWE 路径长期并存本身就是天然的降级路径——Privy 不可用时用户仍可用外部钱包登录（前提是前端有明确的"Privy 登录失败，尝试传统钱包登录"引导，属于 T-1601 的真实实现范围，需要在设计时明确写清） |
| embedded wallet 恢复流程（密码/passkey/MFA）被社工攻击绕过 | Privy 官方文档描述的真实恢复机制固有风险——任何"账号恢复"机制都天然是社工攻击的目标 | 中（行业通病，非 Privy 特有） | 高——恢复流程被绕过等价于账户接管 | 本项目不实现自己的恢复逻辑（不重复造轮子，Privy 的恢复 UI/流程由 Privy SDK 提供），但需要在前端集成时使用 Privy 官方推荐的 MFA 强化配置（passkey 优先于纯密码），这是 T-1601 实现时的真实配置项，不是本文档能替代验证的——T-1601 完成后需要有真实的恢复流程演练证据 |
| 本项目数据库/日志间接持久化了可用于重建密钥的信息（即使不是私钥本身，例如缓存了 auth share 或恢复因子） | 本项目自己实现时的真实风险——"不存私钥"容易被误解为"不存私钥字符串"，但分片/恢复因子同样敏感 | 低（只要严格遵守"只存 address"的接口边界） | 极高——等价于存了私钥的等价物 | `PrivyIdentityProvider` 实现审查时必须显式确认：不缓存、不记录、不通过任何调试接口暴露 Privy SDK 返回的任何非 `address` 字段；这条要求写入 T-1601 的验证清单，不是隐含假设 |

## 未决/需要 T-1601 实际集成时重新核实的事项

- ADR 已如实记录：Privy 公开资料中"2-of-2 enclave+auth share"与"3-of-3 device+auth+recovery share"两套架构描述并存，本威胁模型的缓解措施建立在"本项目后端永远拿不到任何 share"这一共同前提上（两套架构下都成立），但恢复流程的具体 UX 细节（密码 vs passkey vs 云恢复）需要 T-1601 实现时对照当时的 Privy 官方文档重新确认一次，不能直接沿用本文档调研时的快照。
- 本项目尚未确定 Privy 的定价/合规（SOC2 等）条款是否满足平台自身的合规要求——这不是技术威胁模型的范围，但 T-1601 编码前如果涉及真实生产环境接入，需要业务侧单独确认（本文档不代替这一步）。
