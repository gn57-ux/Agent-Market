## 本项目在恢复流程中的真实角色

**本项目不实现、不参与、不代理任何私钥恢复逻辑。** 私钥恢复完全由 Privy 官方 SDK/基础设施负责——这不是"图省事的简化"，而是直接来自威胁模型的结论：本项目后端设计为永远拿不到私钥、share 或恢复因子本身，因此本项目物理上无法自己实现恢复逻辑（没有可操作的密钥材料），也不应该尝试绕过 Privy 的架构去"自己存一份恢复信息"（那会直接违反"不在普通数据库保存私钥"的硬约束，且制造一个 Privy 架构本身没有的新泄漏面）。

## 真实恢复路径（依据 Privy 官方文档核实）

根据 Privy 官方文档（`docs.privy.io`，2026-09-01 核实），用户在新设备/丢失设备场景下的恢复依赖以下机制之一，由 Privy SDK 在前端直接驱动：

- **密码恢复**：用户在新设备/浏览器尝试使用 embedded wallet 时，Privy SDK 自动提示输入之前设置的密码。
- **Passkey/MFA 恢复**：用户已启用 wallet MFA 的情况下，通过注册过的 passkey（通常是设备生物识别）完成验证；启用 MFA 后，任何需要使用私钥的操作（含恢复）都需要完成 MFA 校验。
- **云恢复（cloud-based recovery）**：Privy 官方博客提及的一项能力，具体机制与本文档调研时的其余细节一致地记录为"需要 T-1601 实现时对照当时最新官方文档重新核实"，不在本文档假设其确切实现细节。

## 本项目需要真实承担的责任

虽然不实现恢复逻辑本身，本项目仍有以下真实、具体的责任（T-1601 的验证清单，不是可选项）：

1. **前端集成时启用 Privy 官方推荐的恢复因子配置**（威胁模型已指出：纯密码恢复的社工攻击面大于 passkey/MFA），具体配置项以 T-1601 实现时的 Privy SDK 版本文档为准。
2. **不缓存、不记录任何恢复相关的用户输入或 Privy 返回值**——包括但不限于密码、passkey 挑战/响应、MFA 验证码；这些数据流完全在用户浏览器与 Privy 基础设施之间，本项目后端不应该在任何请求路径上看到这些内容，如果实现中发现后端确实接触到了这类数据，必须视为设计缺陷立即修正，不得"先上线再说"。
3. **在前端明确告知用户**：embedded wallet 的恢复凭据（密码/passkey）由 Privy 管理，不是本项目的账号密码，用户如果同时使用传统 SIWE 登录，两套凭据完全独立，互不代替（避免用户误以为"记得平台密码就能找回钱包"这类真实存在的用户理解偏差）。
4. **SIWE 路径作为真实的降级退出通道**：如果用户的 Privy embedded wallet 因任何原因（包括恢复流程失败）无法访问，且该用户之前也用过外部钱包（MetaMask）登录过同一地址，用户仍可以通过 SIWE 路径继续使用本项目——这依赖 F-1603 已验证的"同一地址、不同身份提供方登录、历史数据仍正确关联"能力（T-1602 的验证范围）。对于**只用过** embedded wallet、从未关联过外部钱包的用户，一旦 Privy 侧恢复流程本身失败，本项目没有任何后备方案——这是真实存在的、必须让用户在使用产品前就知晓的风险边界，需要在 T-1601 的前端实现中有真实的提示文案，不能假装不存在这个边界。

## 失败演练要求（T-1601 完成后的真实验证，不是纸面演练）

T-1601 实现完成后，必须有以下真实场景的可复现证据（不是构造断言，是真实操作）：

- 一个真实测试账户，完整走一遍"注册 embedded wallet → 模拟清除本地设备状态 → 通过密码/passkey 恢复 → 恢复后地址不变、历史数据仍正确关联"的真实流程。
- 确认恢复流程中，本项目后端的请求日志/响应体不包含任何密码、passkey 挑战数据、Privy token（复用 AC-1602 的抓包审查方法）。
