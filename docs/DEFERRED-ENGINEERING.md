# 延期工程能力记录

> 状态：`DEFERRED`  
> 当前阶段：不实施  
> 重新评审时间：Agent Market 第一期和第二期均完成后

## 1. 文档目的

本文档记录已经评估、但为控制当前项目复杂度而主动延期的工程能力。这些条目不是第一期或第二期的需求、Feature、Task 或验收标准，也不构成预留实现的授权。

延期项只有在出现真实消费者、重复实现、已证明的维护成本、性能瓶颈或故障案例后，才能逐项重新评审。

## 2. 统一延期规则

对本文档中的每个条目，统一适用以下规则：

- 当前不创建空目录、占位接口、数据表、无消费者抽象、预备依赖或伪测试。
- 不得由 `/yd:prd` 将延期项生成一期或二期 Feature、Task 或 AC。
- “未来可能需要”、“保持架构完整”或“先预留”不是启动实现的充分理由。
- 重新启动前必须定义当前行为、具体问题、至少两个方案、失败条件、验证方法和回滚方式。
- 优先修正局部实现；只有局部修正无法解决已证明的问题时，才增加通用抽象或新基础设施。

## 3. 延期能力

### 3.1 通用多步骤交易工作流引擎

当前一笔钱包交易由简单交易状态机管理；`approve + 业务交易` 由发布、接单等业务 Feature 显式编排。

只有当至少三个业务流程出现相同的三步及以上交易序列，且重复逻辑已实际导致状态恢复错误或明显维护成本时，才评审是否引入通用工作流引擎。

### 3.2 任务详情动态插件系统

当前任务详情页显式组合各业务区块，不使用模块加载副作用、全局注册表或插件发现机制。

只有出现第三方独立扩展、运行时动态加载或无法在同一发布节奏中显式组合区块的真实需求时，才评审插件系统。

### 3.3 自定义 ESLint 插件与语义规则

当前使用成熟 ESLint 规则禁止 `any` 和非空断言；模糊布尔状态、业务常量归属和模块边界由类型设计、代码审查及普通导入限制保障。

只有同一类错误多次逃过现有规则并造成缺陷，且能以低误报率定义稳定语义检查时，才开发自定义规则。

### 3.4 全仓库链配置、地址和错误码字面量扫描

当前通过单一配置/错误码模块、常规 ESLint 限制和代码审查避免重复字面量。

只有硬编码多次导致环境错误、资金安全问题或大量重复修改，并且普通静态限制无法覆盖时，才增加专用扫描工具。

### 3.5 完整组件框架与主题引擎

当前只实现一期和二期页面已经消费的共享组件及设计 token，不建立无消费者变体、插件 API 或独立主题系统。

只有品牌换肤、多产品共用或多个项目需要稳定组件契约时，才评审完整组件框架。

### 3.6 跨 Feature 自动契约生成

当前使用明确的 API、ABI、JSON 契约和集成测试保持 TypeScript、Go 和 Solidity 边界对齐，不提前引入通用代码生成管线。

只有手工维护契约多次导致联调缺陷，或接口数量达到人工同步显著增加修改成本时，才评审 OpenAPI/ABI 代码生成。

### 3.7 多存储后端抽象

当前仅实现一期需要的本地文件存储，保留最小的 `save/read` 边界，不预先接入 R2/S3、存储选择器或多实现配置。

只有出现实际部署持久性要求、多环境存储需求或本地磁盘已无法满足可用性时，才新增对象存储实现。

### 3.8 更复杂的交易恢复、离线队列与状态持久化

当前只保证页面刷新后能通过后端状态和链上投影恢复，RPC 暂时不可用保持可重试状态。不在一期引入离线交易队列、通用持久化流程引擎或后台重放系统。

只有真实网络故障、大量挂起交易或长时间离线场景已证明基础恢复方案不足时，才评审这些能力。

## 4. 重新评审模板

一期和二期完成后，如某个延期项触发了重新评审条件，应先记录：

1. 当前行为与可重现问题。
2. 影响范围和真实消费者。
3. 保持现状、局部修正、通用能力三个方案的比较。
4. 验证方法、失败条件和可量化收益。
5. 迁移、兼容和回滚方式。
6. 不实施的风险与延期成本。

重新评审不等于自动批准实施；只有评审证据证明新能力能净降低系统复杂度时，才进入新的需求和设计流程。
