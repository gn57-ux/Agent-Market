# ADR-0001: 使用单一 Monorepo 而非多仓库

- 状态：已采纳
- 日期：2026-08-21
- 相关 Feature/Task：Feature 1 / T-001

## 问题

项目需要同时维护四个技术栈（React/TS 前端、Fastify/TS 后端、Go 撮合服务、Solidity/Hardhat 合约），需要决定它们是放在同一个仓库（Monorepo）还是各自独立仓库（Polyrepo）。这个决定影响后续所有 Feature 的目录结构、CI 组织和跨模块修改的操作方式，越早确定越好。

## 已知事实与约束

- 课程/项目周期为 6 周（一期），团队规模小，模块间联调频繁（前端依赖后端 API 契约，后端依赖 Go 撮合服务和合约 ABI）。
- PRD §14.5 推荐了一个跨 `apps/`、`services/`、`contracts/`、`packages/` 的目录结构。
- 一期不涉及独立发布节奏或独立团队权限隔离的需求。

## 方案比较

| 维度 | 方案 A：Polyrepo（每个模块一个仓库） | 方案 B：Monorepo（单一仓库） |
|---|---|---|
| 接口复杂度 | 跨仓库契约变更需要分别提交、分别发版协调 | 单次提交可跨模块原子化修改（如同时改 API 路由和前端调用） |
| 模块依赖 | 依赖通过包发布/子模块引用，版本滞后 | `packages/domain` 等共享包可直接被 workspace 引用，无需发布 |
| 可测试性 | 端到端联调需要拉取并对齐多个仓库版本 | 单仓库本地即可起完整环境跑通交易闭环 |
| 修改成本 | 6 周周期内协调多仓库版本是明显负担 | 低，符合课程交付节奏 |
| 回滚方式 | 每仓库独立回滚，跨仓库联动变更难以追溯到同一个时间点 | Git 提交级别可追溯；子目录仍可在未来按需拆分独立发布 |

## 选择

选择方案 B（Monorepo）。核心理由：一期的开发模式是跨模块高频联调（合约 ABI 变化影响后端复核逻辑，后端契约变化影响前端调用），Polyrepo 在这种模式下的协调成本会直接拖慢 6 周交付节奏；而 Monorepo 在没有独立发布/权限隔离需求的阶段，没有明显的反向代价。使用 `pnpm workspace`（`pnpm-workspace.yaml`）组织 `apps/*`、`contracts`、`packages/*` 作为 workspace 成员。

## 失败条件

- 若后续某个模块（如合约）需要独立于其他模块的发布节奏、独立的访问权限，或团队规模扩大到需要仓库级权限隔离，则 Monorepo 的优势会反转。
- 若 CI 构建时间因为单仓库全量检查而显著拖慢日常提交反馈速度，且路径过滤不足以缓解。

## 回滚方式

将 `apps/`、`services/`、`contracts/` 各自的 Git 历史通过 `git filter-repo` 或等效工具拆分导出为独立仓库，保留提交历史；成本随仓库拆分时机推迟而增加（依赖数量、跨模块耦合会随时间增长）。
