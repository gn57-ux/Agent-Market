## 1. 文档定位

本文档是一期与二期之间的阶段执行文件。它将最新会议纪要整理成可串行交付的增量，但不替代业务 PRD，也不授权在一期完成前生成二期代码。

需求解释优先级如下：

1. 用户在当前会话中的明确决定。
2. 2026-08-27 最新会议纪要。
3. `docs/PRD-Agent-Market.md` 的二期边界与验收参考。
4. `docs/PROJECT-PLAN-Agent-Market.md` 的跨阶段架构和质量门禁。
5. `docs/DEFERRED-ENGINEERING.md` 的延期规则。

发生冲突时必须记录 ADR，不得由实现者自行选择高风险语义。

## 2. 启动门禁与开发方式

只有以下条件全部满足，才能启动二期：

- 一期集成分支完成全栈 QA，并经人工批准合并 main。
- 一期没有未关闭的 P0/P1；接受风险必须有决策人、理由和证据。
- 一期数据库、合约、API、Go、Web、真实浏览器和真实链行为形成可重复基线。
- Agent 调用凭据、任务专家类型、Embedding Provider 和评分信号的待确认项已有决定。

整体剩余开发固定为两天时间盒的串行 MVP：

- 唯一开发仓库：`/Users/ruolan/Documents/Agent Market`。
- 一期通过并合并 main 后，才从最终 main 创建唯一长期分支 `phase/2`。
- 不创建 Feature worktree，不并行开发 Feature。
- 严格按“Agent/任务差距 -> 向量与评分 -> 集成验收”推进。
- 每个 Feature 完成 YD N1-N8、质量门禁和提交后，才能开始下一个。
- 未经人工授权不得 push、PR 或合并 main。

### 3.1 不直接照字面实现

- “三个钱包”不等于平台托管三把私钥。
- “不支持第三方框架”不等于把协议绑定到某个未确认 SDK；应实现平台版本化协议和兼容测试。
- “向三个 Agent 发请求”不等于修改一期任务让三个 Agent 同时获得结算权；执行候选和资金受益人必须分开建模。
- “自动打款”仍必须服从合约状态机、确认数、幂等和争议窗口。
- “洗牌”不能绕过资格过滤、接单授权、预算或安全约束。
- 白板中的 `key` 只允许解释为密钥服务中的凭据引用；不得保存或返回明文 Agent API key。
- 白板中的 MetaMask 与最新会议的 Privy 通过同一身份提供方边界兼容，不建立两套业务身份。
- 白板评分旁的 `0.21` 缺少变量、单位和公式上下文，保持为待确认信息，不进入实现。
- SQS/SNS/DLQ、AWS/ECS 和仲裁委员会属于生产化候选，不自动进入两天 MVP。
- 第二份纪要中的 BERT、知识图谱/RAG 和 Qwen 路由针对 AI 客服高风险问答，不属于 Agent Market 两天增量；只吸收“资格/意图门禁先于自动化、固定事实不得由模型编造”的工程原则。

## 4. 跨阶段关键设计比较与选择

本节保留会议新增能力的设计边界，但 Privy、三类资金视图、多 Agent 和虚拟办公室的实现均已移到阶段三，不计入当前二期完成。

### 4.1 Privy 接入

| 维度 | 方案 A：直接替换一期 MetaMask | 方案 B：身份提供方适配器，Privy 为默认 |
|---|---|---|
| 接口复杂度 | 表面较低 | 增加一个稳定边界 |
| 兼容性 | 已有地址和会话可能失效 | 可迁移、可双轨验证、可回滚 |
| 知识归属 | Privy 细节容易泄漏到页面 | 认证模块集中拥有提供方差异 |
| 测试 | 只能围绕新路径重写 | 可复用一期契约并补 provider contract test |
| 回滚 | 困难 | 切换配置即可回退 |

选择方案 B。公共业务接口只暴露已验证的钱包地址和会话，不向下游泄漏 Privy token 或 SDK 对象。

### 4.2 三类资金模型

| 维度 | 方案 A：平台创建并托管三个真实钱包 | 方案 B：用户钱包 + 合约事实 + 三类只读资金视图 |
|---|---|---|
| 安全风险 | 私钥托管、恢复、合规风险高 | 不新增托管面 |
| 一期兼容 | 需要迁移资金与地址语义 | 复用现有地址和 TaskEscrow |
| 可核对性 | 依赖平台内部账本 | 每项可追溯到链上事件或业务记录 |
| 回滚 | 涉及资产迁移 | 删除聚合层即可 |

选择方案 B 作为默认计划。若课程明确要求三个独立链上地址，必须先新增 ADR、威胁模型和恢复方案，再决定是否使用 Privy embedded wallets；不得在普通业务数据库保存私钥。

### 4.3 多 Agent 编排

| 维度 | 方案 A：业务状态直接存入 LangGraph | 方案 B：Agent Market 拥有领域状态，LangGraph 只执行 |
|---|---|---|
| 框架耦合 | 高 | 低 |
| 资金一致性 | 框架恢复可能与链状态冲突 | 合约和业务事务继续是事实源 |
| 可测试性 | 需要启动框架才能测业务 | 领域逻辑可独立测试 |
| 回滚 | 更换框架困难 | 可切到人工执行器 |

选择方案 B。LangGraph 通过窄适配器接收已验证计划并回传节点执行结果，不拥有预算、结算、权限或最终任务状态。

### 4.4 虚拟办公室

个人/多人描述产品访问范围，2D/3D 描述渲染技术，两者不能作为两套办公室重复建设。

| 维度 | 方案 A：个人办公室同时实现 2D 和 3D | 方案 B：一套办公室业务模型，渲染方式二选一 |
|---|---|---|
| 交付风险 | 重复页面、测试和状态同步 | 只维护一个实现 |
| 业务模型 | 容易随渲染技术分叉 | 工位、Agent、状态和权限保持稳定 |
| 技术升级 | 需要迁移两套交互 | 可替换 renderer 而不改业务接口 |
| 回滚 | 两套实现互相依赖 | 独立页面或 renderer 可关闭 |

选择方案 B。阶段三使用 Cocos Creator 建设一套个人办公室，在 2D 与轻量 3D 中择一；默认从轻量 2D/等距场景起步。后续只在同一模块增加访问权限和社交，是否升级 3D 是独立技术决策。

## 5. 两天基础增强串行计划

时间盒只压缩范围，不压缩安全和质量门禁。Embedding Provider 或 pgvector 环境缺失时必须报告阻塞，不能用 mock 宣称真实集成。

### 第一天上午：一期最终收口

1. 完成 integration/phase1 的真实 PostgreSQL、Go、Hardhat/RPC、API、Web 和浏览器最终 N6。
2. 发现 P0/P1/P2 立即停止；全绿后等待人工 QA，再合并 main。
3. 从最终 main 创建唯一 `phase/2` 分支；不创建新的 Feature worktree。

退出条件：一期有可重复全栈基线，main 合并后 smoke test 通过。

### 第一天下午：Agent/任务字段与凭据安全

1. 冻结一期回归，建立白板要求到现有字段的差距测试。
2. Agent 补充作者简介、调用地址、平台协议版本和凭据引用。
3. 凭据只保存密钥服务引用或加密引用；API、日志和错误不得返回明文。
4. 任务补充专家类型，使用明确领域枚举和运行时校验。
5. 创建和调用请求使用调用方生成的幂等键；拒绝空值、重复冲突和固定全局 request ID。

退出条件：新增字段迁移 up/down/up 通过；明文 key 不进入数据库、API、日志或测试快照；重复请求不会产生重复 Agent 或调用记录。

### 第二天上午：向量召回与评分信号

1. 接入 pgvector 与真实 Embedding Provider，完成关键词 + 向量召回及 V0 降级。
2. 在 Go 中集中实现完成强度、质量反馈、沟通体验、争议率和历史完成规模信号。
3. 每个信号定义范围、缺失值、样本窗口和唯一数据源；不得在调用方复制公式。
4. 保留现有资格过滤和新人探索，保存算法版本、特征摘要和推荐解释。
5. 用小型人工标注集和黄金样本验证相关性、确定性与降级。

退出条件：资格过滤不能被向量或评分绕过；Provider 故障回退 V0；`0.21` 未经确认不进入公式；相同版本和输入可回放。

### 第二天下午：完整集成与演示证据

1. 串通 Agent 发布、任务发布、向量匹配、最多 3 个候选、接单、交付和结算。
2. 验证向量故障回退 V0、资格过滤不可绕过、凭据脱敏和幂等冲突。
3. 运行一期全栈回归、真实 PostgreSQL、Go、Hardhat、Web 和浏览器门禁。
4. 输出白板验收矩阵，明确一期已有、二期新增和阶段三延期项。

退出条件：白板基本要求的真实差距均有代码和证据；一期资金闭环无回归；所有阶段三项目明确不计入二期完成。

## 7. 每个增量的统一质量门禁

- 实际 diff、规格和测试证据必须人工或独立代理读取，不能只看测试数量。
- TypeScript typecheck、Lint、格式、生产构建。
- API 单元/真实数据库集成测试和迁移 up/down/up。
- Go test/vet/gofmt/基准与黄金样本。
- 合约 compile/test、资金守恒和真实 Hardhat/RPC 验证。
- 身份、资金、评分和工作流属于高风险，N6 必须有故障注入和真实边界证据，并等待人工 qa-pass。
- 当前增量的 Embedding Provider 必须有超时、限流、失败降级、脱敏和关闭开关测试；Privy、AI 评测和 LangGraph 的同类门禁在阶段三启用。
- 每个增量完成后重新运行一期全栈回归。

## 8. 启动前必须确认的决定

### 8.1 阶段二阻断项

1. Agent `key` 的实际含义、凭据存储服务和轮换/撤销方式。
2. Agent 调用地址使用 HTTP、流式协议还是其他平台协议，以及超时和鉴权规范。
3. 任务“专家类型”的枚举、是否允许多选以及与分类/标签的关系。
4. Embedding Provider、模型版本、维度、成本上限和失败策略。
5. 完成强度、质量反馈、沟通体验、争议率和历史完成规模的范围、缺失值与窗口。
6. 白板中的 `0.21` 表示阈值、权重、样例分数还是其他指标；未确认前不得使用。

### 8.2 阶段三再确认

1. Privy 钱包类型、MetaMask 迁移和账户恢复。
2. 三类资金视图或三个真实钱包的所有权与安全边界。
3. 免费/付费 Agent 审核规则。
4. LangGraph、多 Agent 付费、未入选结果补偿和子任务预算。
5. Cocos 个人办公室采用 2D 还是轻量 3D、最低交互和社交边界。
6. 仲裁委员会成员、投票规则和合约升级方式。
7. SQS/SNS、DLQ、AWS/ECS 的真实部署与恢复需求。

阶段二阻断项未确认前，可以进行只读调研和方案比较，但不得生成不可逆迁移或用假数据掩盖缺口。阶段三事项不阻塞阶段二。
